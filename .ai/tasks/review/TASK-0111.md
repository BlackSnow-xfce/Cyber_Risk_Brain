# TASK-0111 – Incident Queue / Investigation Overview – Operational Foundation

**Status:** REVIEW / REWORK REQUIRED  
**Reviewer:** Architect  
**Track:** Post-MVP Product Integration / Incident Responder

## Objective

Create a read-only operational Incident Queue / Investigation Overview inside
the existing Incident Responder workspace. The analyst must be able to see
real persisted Incidents, search/filter them, understand supported state, open
the existing Command Center, and use reliable browser navigation.

No new Incident domain model is introduced.

## Authoritative Incident Data

`core/incident_response/context.py` and `SecurityIncidentContext 1.0` remain
authoritative. The queue may expose only existing fields, including where
present:

* `incident_id`, title and lifecycle status;
* source and source reference;
* created/updated timestamps;
* owner and participant count;
* typed Finding, Asset, Threat Intelligence and Evidence relationship counts.

Do not invent severity, priority, risk, confidence, compromise, SLA,
business impact or response state. Absence of such fields remains absent.

## Repository List Boundary

Extend the existing `FileIncidentContextRepository` with the smallest
read-only list capability needed to enumerate persisted
`SecurityIncidentContext` objects. Reuse the existing persistence file/store,
strict schema validation, canonical deserialization and fail-closed malformed
data behavior. Do not add a second store, database or pagination framework
unless the existing runtime concretely requires it. Listing must not add write
behavior.

## Application Read Service

Add or extend the smallest appropriate Application-layer read service for
listing canonical Incident Contexts. Retrieval belongs in the Application
layer, not in the frontend. No mutation, lifecycle transition, assignment,
notes, activities or remediation is part of this task.

## Incident List API

Add the minimal read-only endpoint:

`GET /api/incidents`

Return an explicit stable queue projection containing only the supported queue
fields. Do not expose persistence implementation details and do not add a
competing Incident Detail API. The existing deep-investigation endpoint
remains authoritative:

`GET /api/incidents/{incident_id}/command-center`

## Incident Queue UI

Operationalize the existing Incident Response queue/overview area using real
data from `GET /api/incidents`. Reuse the current workspace, routing and
visual language. Display supported title, canonical incident ID, lifecycle,
owner, timestamps, source and useful relationship counts where available.
Each incident must offer an action to open the existing Command Center while
preserving the exact canonical `incident_id`.

## Search and Filter

Implement compact client-side filtering over the already loaded canonical
Incident list. Matching is case-insensitive, partial and immediate across
meaningful available fields: incident ID, title, lifecycle, owner and source.
An empty query restores all loaded incidents; no matches show an explicit
no-results state. Filtering must never change Incident identity or navigation
targets. No backend search engine is required.

## Command Center Drill-down

Use the existing technical deep-dive route exactly:

`/incident-response/incidents/<incidentId>/command-center`

Do not create a competing Incident Detail workflow or redesign the Command
Center.

The known runtime incident `incident-task0077-distcc-live` may be used for
live validation if present, but must never be hardcoded as queue data or
introduced as a mock.

## URL-authoritative Incident Response Navigation

For registered Incident Response areas, `location.pathname` must be
authoritative for the rendered area. Correct the existing stale
`activeNavigationItemId` behavior without introducing a second routing state
machine or redesigning global routing. Preserve direct links, workspace
switching, Browser Back/Forward and Command Center deep links.

## Empty and Error States

An empty repository renders an explicit empty operational state with no sample
incidents. Retrieval failure renders a transparent error state and must not be
silently presented as an empty successful queue.

## Incident Semantic Invariants

1. Finding is not an Incident.
2. Threat Intelligence is not Evidence.
3. An Evidence reference is not a resolved Evidence object.
4. Incident lifecycle is workflow state and does not prove compromise.
5. AI output has no Incident authority.
6. Queue display must not invent severity, priority, confidence, compromise,
   impact or response state absent from the canonical contract.
7. The canonical `incident_id` survives loading, search, filtering and
   Command Center navigation unchanged.

## Existing Command Center Boundary

Reuse the existing Command Center API and presentation. Its known limitations
remain explicit and are outside this task unless strictly required for queue
integration: Evidence references are not resolved to Evidence objects;
activities and Analyst Notes may be runtime-empty; lifecycle transitions are
not persistently/API connected; completeness may remain `no_data` or expose
missing context. Do not fabricate data to hide these states.

## Explicit Non-goals

Do not implement lifecycle mutation, Incident creation/deletion, owner or
participant mutation, Analyst Note writes, Activity persistence, collaboration
or case-management platforms, Evidence resolution, priority/severity/risk
engines, automated Incident creation, SOAR, containment/remediation, EDR/SIEM
or ticketing integrations, AI Incident Commander, autonomous agents, a new
persistence platform/database, or a Command Center redesign. Do not add
TASK-0112.
