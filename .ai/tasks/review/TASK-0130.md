# TASK-0130 - Authoritative Service Impact Profile & Business-Impact Classification Readiness

Status: REVIEW / REWORK REQUIRED
Reviewer: Architect
Architect Task-Specification Review: PASS / APPROVED
Architect Implementation Review: FAIL / REWORK REQUIRED
Product Owner Live Acceptance: PENDING / NOT READY

## Objective

Extend the existing Finding Risk Context with authoritative service-level CIA
business importance, a provenance-preserving technical-effect projection, and a
distinct downstream Business-Impact Classification Readiness result.

Business Impact means the expected organizational consequence if the specific
finding is successfully exploited under the currently supported,
evidence-backed technical scenario. TASK-0130 does not calculate or classify
that consequence. `business_impact` remains `None`/`null`.

## Semantic Separation

The following authorities are distinct and never substitutable:

- `AssetCriticality`
- `ServiceCriticality`
- `DecisionPriority` / `FindingRiskPriority`
- technical severity, exploitation likelihood, CVSS score
- `BusinessImportance`
- future Business Impact

No technical signal, priority, or existing criticality may populate CIA
business importance.

## BusinessImportance Authority

Create a new immutable enterprise-context enum `BusinessImportance` because no
existing type has the approved CIA business-importance semantics. Exact values:

- `CRITICAL`
- `HIGH`
- `MEDIUM`
- `LOW`

Runtime values must be actual `BusinessImportance` members inside the domain.
Strings, other enums, coercion, case normalization, fallback, and matching-label
substitution are invalid.

## ServiceImpactProfile Domain Contract

Create an immutable `ServiceImpactProfile` containing exactly:

- `canonical_asset_id: str`
- `business_service: str`
- `confidentiality_importance: BusinessImportance`
- `integrity_importance: BusinessImportance`
- `availability_importance: BusinessImportance`
- `source_reference: str`

All strings are non-empty and must already be canonical: leading/trailing
whitespace is rejected rather than normalized. All three CIA dimensions are
mandatory. The source reference applies to every profile fact and must survive
resolution, readiness, API serialization, and frontend rendering.

## Strict JSON Authority

The configured Product-Owner-controlled JSON source has exactly this schema:

```json
{
  "serviceImpactProfiles": [
    {
      "canonicalAssetId": "asset-id",
      "businessService": "Service name",
      "confidentialityImportance": "HIGH",
      "integrityImportance": "CRITICAL",
      "availabilityImportance": "CRITICAL",
      "sourceReference": "authoritative-system:record-id"
    }
  ]
}
```

The root and record key sets are exact. Values are not trimmed or converted.
Unknown keys, missing keys, non-string values, whitespace-padded values,
invalid enums, duplicate canonical assets, duplicate exact records, or
conflicting records fail closed with a dedicated controlled data error. An
unconfigured source or absent canonical-asset record returns truthful absence.
The source path is configured by `SERVICE_IMPACT_PROFILE_PATH`; no profile data
is committed by this task.

## Finding Profile Resolution

Create an immutable finding-scoped resolution with states:

- `RESOLVED`
- `NOT_FOUND`
- `MISSING_CANONICAL_ASSET`

Resolution consumes the existing TASK-0129 business-context resolution and
queries by canonical asset, never by service name alone. A RESOLVED profile must
match both `canonical_asset_id` and the exact `business_service` snapshot from
`AssetBusinessContext`. Any mismatch raises a dedicated integrity error. Missing
TASK-0129 context, duplicate/conflicting source data, and missing records are not
silently normalized or inferred.

## Technical-Effect Authority

Create an immutable application projection from the existing authoritative
finding Threat Intelligence snapshot. It is technical effect, not business
importance or Business Impact.

Supported policy is deliberately finite:

- only applicable TI relationships with available NVD CVSS facts;
- only CVSS versions `3.0` and `3.1`;
- vector prefix must exactly match the declared version;
- exactly one each of `C`, `I`, and `A` must exist;
- their exact metric values are `N`, `L`, or `H`, projected to a new technical
  `TechnicalEffectLevel.NONE`, `.LOW`, or `.HIGH`;
- duplicated, missing, malformed, conflicting, or unsupported metrics fail
  closed and are enumerated as missing/unsupported requirements;
- CVSS base score, severity, EPSS, KEV, vendor severity and exposure never
  establish technical effect.

Each immutable effect item contains `finding_id`, `cve_identifier`,
`cvss_version`, the three technical effect levels, original vector,
`source_reference`, and `observed_at`. Preserve the original CVSS fact
provenance and observation time exactly. Multiple applicable CVEs remain
separate effect items; no aggregation or worst-case selection is performed.

The finding projection exposes `AVAILABLE` or `UNAVAILABLE`, exact effect items,
missing requirements, source references, and existing Explainability
completeness/provenance. It is AVAILABLE only when at least one applicable
effect exists and every applicable relationship is supported and proven.
Unsupported CVSS v2/v4, missing CVSS, non-applicable TI, ambiguity, or malformed
vectors remain UNAVAILABLE. No LLM or provider call is permitted.

## Business-Impact Classification Readiness

Create a distinct immutable result; do not repurpose TASK-0129
`BusinessImpactReadiness`.

Schema:

- `finding_id: str`
- `status: BusinessImpactClassificationReadinessStatus`
- `reason: str`
- `business_facts: tuple[BusinessContextFact, ...]`
- `service_impact_facts: tuple[ServiceImpactFact, ...]`
- `technical_effects: tuple[FindingTechnicalEffect, ...]`
- `missing_requirements: tuple[str, ...]`
- `source_references: tuple[str, ...]`
- `completeness: ExplanationCompleteness`

States are exactly `READY` and `UNAVAILABLE`. READY requires:

1. TASK-0129 business context and Business-Impact Readiness are READY and
   mutually consistent.
2. Service Impact Profile is RESOLVED for the same finding, canonical asset and
   exact business service.
3. All three CIA BusinessImportance facts are present, runtime-valid and proven.
4. The technical-effect projection is AVAILABLE, contains at least one valid
   effect, and preserves CVSS provenance and `observed_at`.
5. All finding/source snapshots agree.
6. Result provenance is exactly
   `business-impact-classification-readiness:ready:<finding_id>` with source type
   `business_impact_classification_readiness` and completeness `AVAILABLE`.
7. `missing_requirements` is empty.

UNAVAILABLE preserves every valid partial fact/effect and provenance, reports
exact missing or unsupported requirements, uses non-AVAILABLE completeness and
deterministic result provenance
`business-impact-classification-readiness:unavailable:<finding_id>`. It never
creates an impact score, band, narrative, consequence, decision, or
recommendation.
