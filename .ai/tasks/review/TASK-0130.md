### Strict CVSS v3 Authority

No strict CVSS parser is present in the repository, declared Python
dependencies, or installed environment. Adding a dependency would broaden the
approved authority and is unnecessary for the finite supported contract.
Implement one internal deterministic parser in
`application/finding_technical_effect.py` with this complete grammar:

- prefix/version pairs are exactly `3.0` plus `CVSS:3.0/`, or `3.1` plus
  `CVSS:3.1/`;
- exactly one of each base metric is required: `AV`, `AC`, `PR`, `UI`, `S`,
  `C`, `I`, `A`;
- allowed values are `AV=N|A|L|P`, `AC=L|H`, `PR=N|L|H`, `UI=N|R`,
  `S=U|C`, and `C|I|A=N|L|H`;
- tokens may be reordered; empty, malformed, duplicate, missing, unknown, or
  invalid tokens fail closed;
- only `C`, `I`, and `A` produce `NONE`, `LOW`, or `HIGH`; all other metrics
  validate source authority only.

No normalization, case conversion, version reconciliation, score fallback, or
partial C/I/A pseudo-vector is permitted.

### Technical Effect Provenance

An AVAILABLE `FindingTechnicalEffect` is immutable and contains:

- `finding_id`;
- `cve_identifier`;
- `cvss_version` matching the vector prefix;
- exact original `cvss_vector`;
- confidentiality, integrity, and availability `TechnicalEffectLevel`;
- `provenance: ExplanationProvenance` copied unchanged from the authoritative
  CVSS `IntelligenceFact`;
- timezone-aware, non-null `observed_at` copied unchanged from that fact.

`provenance.source_type` must be exactly `nvd`; both provenance fields are
non-empty under the existing Explainability invariant. An effect lacking any
identity, version, vector, provenance, or observation time cannot be AVAILABLE
or satisfy classification readiness. Projection-level deterministic provenance
remains `finding_technical_effect` with the approved status/finding reference.

### Mixed Applicable-CVE Policy

Each applicable CVE is evaluated independently and retains its own vector,
timestamp, and provenance. Duplicate CVE identities are controlled integrity
failures. If every applicable relationship is supported and authority-complete,
the projection is AVAILABLE with separate ordered effects. If any applicable
relationship is unsupported, malformed, or provenance-deficient, the projection
is UNAVAILABLE with a CVE-specific missing requirement. Other valid effects may
be retained only as explicit partial authority; they cannot be aggregated,
reclassified, interpreted as NONE/LOW, or make Classification Readiness READY.
A non-applicable relationship never produces an effect; with no complete
applicable relationship the projection is UNAVAILABLE.

### Classification Readiness Gate

READY requires an AVAILABLE Technical Effect projection and independently
validates every included effect's finding/CVE identity, exact supported
version/vector pair, NVD provenance, source reference, timezone-aware
`observed_at`, and unique CVE identity. Any partial or deficient projection is
UNAVAILABLE and preserves exact missing requirements plus valid partial
authority. Business Impact remains null; no impact matrix, score, band, or
narrative is authorized.

### API Source Binding

Each serialized effect contains `finding_id`, `cve_identifier`, `cvss_version`,
`cvss_vector`, technical C/I/A values, `observed_at`, `source_type`, and
`source_reference`. Together, finding+CVE+version+vector+provenance+timestamp form
the minimal binding identity to the existing transported TI relationship and
its CVSS fact. Classification readiness carries exactly the same effect objects,
not a lossy reconstruction.

### Frontend Snapshot Binding

The parser must locate exactly one applicable transported TI relationship for
each effect CVE and require its available CVSS fact to match effect finding,
CVE, metadata version, vector, provenance source type/reference, and
`observed_at` exactly. It independently parses the strict vector grammar and
verifies derived C/I/A levels. It then requires Classification Readiness effects
to equal the already source-bound Technical Effect projection. Duplicate or
unmatched TI/effect identities, altered values, provenance, timestamps, or CIA
levels fail closed even if both effect copies were changed together.

AVAILABLE effects reject missing/null/invalid timestamps or provenance.
UNAVAILABLE partial effects, when present, must individually remain valid and
source-bound and never promote the result to READY.
