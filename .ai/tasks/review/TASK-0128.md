# TASK-0128 - Evidence-Gated Finding Risk Priority

Status: REVIEW / ARCHITECT PENDING

Product Owner Live Acceptance: PENDING / NOT READY

## Objective

Extend the existing read-only Finding Risk Context projection with the first
downstream risk-management capability: an evidence-gated, deterministic and
explainable Finding risk priority, or an explicit truthful unavailable result.

The authoritative chain is:

`Finding -> FindingRiskContext -> context readiness + evidence readiness ->
RiskPriority or explicit refusal`.

TASK-0128 does not create a score, business impact, treatment, decision or
recommendation authority. It classifies only a score already produced by the
existing gated `RiskReadinessService` and only when canonical evidence is also
ready.

## Architectural Boundary

- Add `application/finding_risk_priority.py` as a deterministic application
  policy over existing immutable `RiskAssessmentResult` and
  `RiskAssessmentReadinessResult` inputs.
- Reuse the existing, frozen `core.decision.priority_engine.PriorityEngine`
  and `DecisionPriority` band contract. Do not copy its thresholds or introduce
  a competing classifier.
- Keep `RiskReadinessService` as the only permitted technical-score boundary.
- Keep `RiskAssessmentReadinessService` as the canonical-evidence gate.
- `FindingRiskContextUseCase` composes the new result after its existing source
  integrity checks and readiness evaluations.
- The API remains the existing read-only endpoint:
  `GET /api/findings/{finding_id}/risk-context`.
- The frontend renders the transported result and performs no classification,
  scoring or inference.

## Immutable Priority Contract

Define an immutable application contract with:

- `finding_id`;
- status exactly `PRIORITIZED` or `UNAVAILABLE`;
- nullable priority band using the existing values `critical`, `high`,
  `medium`, `low`, `informational`;
- nullable source risk score;
- deterministic reason;
- considered correlation Evidence IDs;
- referenced authoritative input/provenance references;
- explicit missing requirements;
- completeness and provenance identifying the priority policy and Finding.

`PRIORITIZED` requires all of the following:

1. context assessment status is `ASSESSED`;
2. the assessment contains a non-null bounded score;
3. evidence readiness status is `READY`;
4. assessment, evidence readiness and requested Finding IDs match;
5. canonical evidence identifiers and referenced input references are retained.

Otherwise status is `UNAVAILABLE`, band and score are null, and the reason and
missing requirements enumerate the failed gates. Unknown and not-evaluated
states must not be converted to false, zero or a default priority.

## Deterministic Band Authority

- Use `PriorityEngine.calculate(score)` unchanged.
- Existing thresholds remain authoritative through that implementation:
  critical `>= 90`, high `>= 75`, medium `>= 50`, low `>= 25`, otherwise
  informational.
- TASK-0128 must not duplicate these thresholds in production code.
- The output describes Finding risk priority only. It must not create or imply
  a `DecisionResult`, analyst decision, management approval or remediation SLA.

## Fail-Closed Requirements

- `INSUFFICIENT_CONTEXT` always yields priority status `UNAVAILABLE`, null band
  and null score, regardless of vendor severity, CVSS, EPSS or CISA KEV data.
- `INSUFFICIENT_EVIDENCE` always yields `UNAVAILABLE`, even if a score-shaped
  value is supplied by a controlled test fixture.
- Finding-ID, evidence-ID, provenance or source-snapshot mismatch fails closed.
- Empty or inconsistent provenance cannot produce a priority.
- Existing `refusal_reason` remains visible and consistent with priority
  unavailability.
- Business impact, decision and recommendations remain respectively `null`,
  `null` and `[]` in every TASK-0128 result.

## REWORK 1 - Priority Gate and Contract Invariants

Architect Implementation Review found one fail-closed gate defect and one
contract-invariant defect. REWORK 1 is limited to these corrections.

### Evidence-Readiness Invariant

- Non-empty `evidence_readiness.missing_requirements` always prevents
  prioritization, regardless of the reported readiness status.
- The contradictory state `READY` plus non-empty missing requirements must be
  handled deterministically by returning truthful `UNAVAILABLE` with the exact
  missing requirements retained, or by raising an explicit source-integrity
  error.
- It must never call the classifier or return `PRIORITIZED`.
- Normal `INSUFFICIENT_EVIDENCE` and `INSUFFICIENT_CONTEXT` behavior remains
  unchanged.

### Immutable Result Invariants

`FindingRiskPriority` must reject invalid state combinations during immutable
contract construction.

- `PRIORITIZED` requires non-null band and bounded authoritative score, empty
  missing requirements, available completeness, and retained evidence/input
  provenance.
- `UNAVAILABLE` requires null band and null score. Its reason must be non-empty;
  missing requirements remain exact and ordered when present.
- Invalid enum/value combinations, contradictory completeness, missing required
  provenance, or fabricated values raise a deterministic `ValueError`.
- No new threshold, classifier, score, Decision, BusinessImpact or
  Recommendation logic is authorized.

### Focused Negative Tests

1. `READY` plus non-empty evidence missing requirements cannot produce
   `PRIORITIZED` and cannot invoke the classifier.
2. `UNAVAILABLE` construction with a band or score is rejected.
3. `PRIORITIZED` construction without band or score is rejected.
4. `PRIORITIZED` construction with missing requirements or unavailable
   completeness is rejected.
5. Valid `PRIORITIZED` construction and existing PriorityEngine classification
   remain unchanged.
6. The normal DistCC projection remains `UNAVAILABLE` with null band/score.
7. Existing missing-context, missing-evidence, identity, provenance and bounded
   score tests remain green.
