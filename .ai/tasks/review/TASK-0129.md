# TASK-0129 - Authoritative Asset Business Context & Business-Impact Readiness

Status: REVIEW / ARCHITECT PENDING
Reviewer: Architect
Architect Task-Specification Review: PASS / APPROVED
Architect Implementation Review: PENDING

## Objective

Extend the existing Finding Risk Context with a separate authoritative Asset
Business Context resolution and a deterministic Business-Impact Readiness
result. The task exposes organizational facts and their provenance only. It
must not calculate, classify, summarize, or otherwise manufacture Business
Impact.

The chain is:

`Finding -> canonical AssetContext -> AssetBusinessContext resolution -> BusinessImpactReadiness`

Existing `FindingRiskContext.business_impact` remains null.

## Architectural Separation

- Existing `AssetContext` remains unchanged and authoritative only for observed
  identifier, canonical asset identity, asset criticality, and its source.
- `AssetCriticality`, `ServiceCriticality`, and Business Impact are distinct
  concepts. Values must never be substituted between them.
- The new business-context authority is linked only by `canonical_asset_id`.
- Legacy Decision/BusinessContext/BusinessImpact models are not sources and are
  never invoked.
- TASK-0127 context/readiness and TASK-0128 priority semantics remain unchanged.

## Immutable Domain Contract

Create `core.enterprise_context.asset_business_context` with:

### `BusinessEnvironment`

New string enum with exactly:

- `PRODUCTION`
- `PRE_PRODUCTION`
- `DEVELOPMENT`
- `TEST`

No existing authoritative environment enum provides these semantics.

### `ServiceCriticality`

New string enum with exactly:

- `CRITICAL`
- `HIGH`
- `MEDIUM`
- `LOW`

It is deliberately distinct from `AssetCriticality`; matching labels do not
create semantic interchangeability.

### `AssetBusinessContext`

Immutable, slot-based value with exactly:

- `canonical_asset_id: str`
- `business_service: str`
- `environment: BusinessEnvironment`
- `service_criticality: ServiceCriticality`
- `source_reference: str`

All identifiers/text and provenance must be non-empty after trimming. Runtime
enum types must be enforced without coercion. The record-level
`source_reference` is the authority for every fact in this 1.0 record; API and
UI projections must retain it beside every displayed fact.

## JSON Authority 1.0

Add `ASSET_BUSINESS_CONTEXT_PATH` through the existing settings convention and
a strict read-only JSON adapter. The exact document is:

```json
{
  "assetBusinessContexts": [
    {
      "canonicalAssetId": "asset-id",
      "businessService": "Service name",
      "environment": "PRODUCTION",
      "serviceCriticality": "CRITICAL",
      "sourceReference": "authoritative-system:record-id"
    }
  ]
}
```

- Root and record keys are exact; unknown or missing keys fail validation.
- Malformed JSON, enum values, identifiers, text, or provenance fail with a
  controlled data error.
- Lookup is by exact normalized `canonical_asset_id`.
- Duplicate matches, including conflicting records for one canonical asset,
  fail with a controlled ambiguity/integrity error; they are never merged.
- An unconfigured source or absent record resolves truthfully as no business
  context for this optional capability and must not break existing Risk Context.
- A configured but unreadable or invalid source fails controlled; it is not
  silently treated as an empty authority.
- No product or test fixture may add invented DistCC business context.

## Finding Resolution

Create `FindingAssetBusinessContextResolutionStatus` with exactly:

- `RESOLVED`
- `NOT_FOUND`
- `MISSING_CANONICAL_ASSET`

The resolver consumes the already-produced `FindingAssetContextResolution`;
it must not reread or independently resolve the Finding or AssetContext.

- Missing/unresolved canonical AssetContext -> `MISSING_CANONICAL_ASSET`.
- Canonical asset with no authority record -> `NOT_FOUND`.
- Exact record -> `RESOLVED` with unchanged domain value.
- Finding ID and canonical-asset snapshot inconsistencies fail closed.

## Business-Impact Readiness

Create immutable `BusinessImpactReadinessStatus` with exactly:

- `READY`
- `UNAVAILABLE`

The result contains:

- `finding_id`
- status and truthful reason
- exact ordered `missing_requirements`
- authoritative fact projections with `name`, `value`, and `source_reference`
- referenced source records
- `ExplanationCompleteness` and provenance

`READY` requires a resolved canonical relationship plus all five approved facts:

- `canonical_asset_relationship`
- `business_service`
- `environment`
- `service_criticality`
- `business_context_provenance`

Any missing fact produces `UNAVAILABLE`, null/absent impact output, exact
missing requirements, and non-AVAILABLE completeness. Invalid result-state
combinations must be rejected at construction.

Readiness is not Business Impact. It produces no score, band, narrative,
financial/operational/regulatory/reputational consequence, crown-jewel claim,
owner, decision, or recommendation.

## Finding Risk Context Integration

Extend the existing `FindingRiskContext` projection with:

- `business_context`
- `business_impact_readiness`

Reuse the one existing AssetContext resolution snapshot. Preserve source
integrity and provenance. Existing risk assessment, evidence readiness,
priority, refusal, decision and recommendation behavior remains unchanged.

`business_impact` remains exactly null for every state.

DistCC/Metasploitable2 has no approved business-context record and must render:

- Business Context: `NOT_FOUND`
- Business Impact Readiness: `UNAVAILABLE`
- Business Impact: null

This is the expected Product Owner acceptance state.

## API Contract

Extend `GET /api/findings/{finding_id}/risk-context` with:

- `business_context.status`
- nullable context fields for canonical asset, service, environment, service
  criticality and record source reference
- `business_context.facts[]`, each retaining its source reference when resolved
- `business_impact_readiness.status`, reason, missing requirements, referenced
  source records, completeness status and provenance

Resolved fields must be all present and type-valid. Non-resolved states expose
no fabricated fact values. `business_impact`, `decision`, and recommendations
remain null/null/empty.

Configuration/data failures follow existing controlled 503/500 source-error
boundaries without exposing local paths or source contents.

## Frontend Contract

Within the existing `FindingRiskContextSection` only:

- Show Business Context status.
- For resolved context, show service, environment and service criticality with
  the authoritative source beside each fact.
- For unavailable context, show the exact truthful state and missing
  requirements.
- Show Business Impact Readiness as READY or UNAVAILABLE while stating that no
  Business Impact has been calculated.
- Never turn readiness, service criticality, asset criticality, priority, CVSS,
  EPSS or KEV into a Business Impact label or visualization.
- The API parser rejects partial, contradictory, unknown-enum, or
  provenance-free payloads.

Do not populate Risk Manager or Executive widgets.

## Focused Tests

### Domain and JSON authority

- Domain accepts only exact enums and non-empty identifiers/facts/provenance.
- Asset and service criticality remain non-interchangeable runtime types.
- Exact JSON schema parses and preserves all values/provenance.
- Unknown/missing keys, malformed enums, empty source reference, malformed JSON
  and unreadable configured sources fail controlled.
- Unknown canonical asset returns no record.
- Duplicate/equal and conflicting records for one canonical ID both fail
  ambiguity/integrity checks.
- Unconfigured optional source returns no record without inventing defaults.

### Resolution and readiness

- Resolved AssetContext plus exact record -> `RESOLVED` and `READY`.
- No business record -> `NOT_FOUND` and `UNAVAILABLE` with exact requirements.
- Missing canonical AssetContext -> `MISSING_CANONICAL_ASSET` and `UNAVAILABLE`.
- Snapshot mismatch fails closed.
- Invalid READY/UNAVAILABLE result combinations are rejected.
- Readiness never invokes legacy BusinessContext, BusinessImpact, Decision,
  Recommendation, Risk, Priority, or AI/provider authorities.

### Integration/API/frontend

- Finding Risk Context uses its existing AssetContext snapshot once.
- API resolved/unavailable payloads retain fact and result provenance.
- Partial/contradictory payloads are rejected by frontend parser.
- UI renders resolved facts and unavailable/missing states truthfully.
- `business_impact` remains null; decision remains null; recommendations remain
  empty.
- DistCC remains `NOT_FOUND` / `UNAVAILABLE` / null without a fixture record.
- Existing TASK-0127/TASK-0128 context, priority, API and frontend tests remain
  green.
