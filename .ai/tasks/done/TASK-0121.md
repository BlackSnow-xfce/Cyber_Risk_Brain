# TASK-0121 - Explainability Rendering and URL-Authoritative Navigation Repair

## Problem Statement

The existing Explainability route has three confirmed defects:

1. `ExplainabilityWorkspace` synchronously invokes the reasoning orchestrator.
   `ReasoningOrchestrator.execute()` calls `crypto.randomUUID()` before its
   current error boundary. On the permitted LAN HTTP origin this API may be
   unavailable, causing an uncaught render failure and leaving only the outer
   application background.
2. `SOCWorkspace` can prioritize stale `activeNavigationItemId` over the current
   pathname. Browser Back/Forward can update the URL without restoring the
   matching sidebar selection and rendered SOC page.
3. Explainability production rendering depends on `MockFindingRepository` and
   lacks truthful loading, unavailable/empty, error, and controlled
   reasoning-failure behavior.

## Objective

Repair the existing Explainability route so it renders safely on the actual LAN
HTTP origin, treats the URL pathname as authoritative, remains synchronized
through Back/Forward and direct deep links, and presents only truthful states
derived from available authoritative context.

This task repairs an existing route. It does not introduce a new Explainability
backend capability or execute an AI provider.

## Data-Integrity and Security Policy

- Backend-owned real data remains authoritative.
- Use an existing productive read path only if it already provides sufficient
  Explainability context.
- When authoritative context is unavailable, render a truthful Explainability
  unavailable/no-context state. Missing context is not a successful explanation.
- Do not invent, infer, or generate Findings, evidence, reasoning steps,
  confidence, verdicts, compromise claims, or explanations.
- Remove production Explainability dependence on `MockFindingRepository`.
- Opening Explainability must not invoke an AI provider or model.
- Do not expose credentials, sessions, prompts, provider responses, or internal
  exception details.

## Functional Requirements

### Rendering safety

- Explainability must not require `crypto.randomUUID()` to exist.
- Session/request identity creation must work safely in permitted browser
  contexts or fail into a controlled visible state.
- Identity-generation and orchestration errors must be caught inside the
  correct boundary.
- A local exception must not destroy the complete application content tree.
- The purple-only blank page is never an accepted state.

### URL-authoritative navigation

- The current pathname determines the rendered SOC page.
- Stale `activeNavigationItemId` must not override browser history.
- URL, sidebar active item, and rendered content remain synchronized for normal
  navigation, Back, Forward, direct load, and refresh.
- Reuse the current navigation architecture; do not introduce another router.

### Truthful page states

Implement visibly distinct states only where backed by real execution paths:

- loading while an existing authoritative retrieval is pending;
- content when sufficient authoritative context exists;
- unavailable/empty when no authoritative context exists;
- retrieval error when a real retrieval boundary fails;
- controlled reasoning/render error when local orchestration cannot complete.

No state may contain mock or fallback security data.

### Deep links

- Fresh `/explainability` loads and refreshes render the application and
  Explainability shell with the appropriate truthful state.
- Missing or invalid identifiers do not crash rendering.
- Existing query parameters may be consumed only when already part of a
  productive contract.

## Implementation Evidence

- `SOCWorkspace` now resolves rendered SOC content exclusively from the current
  pathname; stale workspace-local navigation state cannot override browser
  history.
- Production Explainability no longer instantiates `MockFindingRepository` or
  performs synchronous reasoning. In the absence of an authoritative
  Explainability read path it presents a truthful unavailable state and performs
  no provider/model request.
- `ReasoningOrchestrator` now contains ID creation inside its controlled failure
  boundary and uses a local, non-authoritative fallback identifier when
  `crypto.randomUUID` is unavailable on an allowed LAN HTTP origin.
- `ExplainabilityPage` contains a narrowly scoped render boundary so a local
  rendering failure leaves the Explainability shell and a controlled error state
  visible instead of collapsing the application content tree.
- Regression coverage proves pathname authority, Dashboard to Explainability,
  Back, Forward, direct deep-link resolution, sidebar/content synchronization,
  unavailable context, absence of retrieval/provider calls, missing
  `crypto.randomUUID`, and controlled ID/render failures.
