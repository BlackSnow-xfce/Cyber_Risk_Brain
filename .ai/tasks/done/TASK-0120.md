# TASK-0120 - Controlled Hunt Hypothesis Activation Foundation

**Status:** DONE / PASS / APPROVED

## Objective

Allow an authenticated and explicitly authorized human Local Operator to move
one existing canonical Hunt Hypothesis from `draft` to `active` through a
narrow, auditable mutation boundary.

`active` means only that the hypothesis is authorized for investigation. It
does not establish truth, confirmation, evidence, successful execution or
compromise.

## Authority and Security Boundary

- Activation requires the exact server-side permission
  `hunt_hypothesis:activate`.
- Reuse the existing Local Operator browser session, exact configured Origin
  check and session-bound CSRF verification.
- Derive principal identity and permissions only from trusted server
  configuration and the validated server-side session.
- Do not accept author, actor, principal, permission, status or other authority
  metadata from the client.
- Missing or invalid authentication fails with the existing `401` semantics;
  authenticated callers without exact authority fail with `403`; unavailable
  or structurally invalid security configuration remains fail closed under the
  existing `503`/generic `500` conventions.

## Lifecycle Contract

- The only permitted transition is exactly `draft -> active`.
- Require an explicit expected source state from the narrow activation request
  and reject stale or mismatched state without mutation.
- Missing hypothesis returns the existing exact resource-not-found semantic.
- `active`, `supported`, `rejected` and `closed` hypotheses cannot be activated
  by this boundary.
- Do not add any other lifecycle transition or general-purpose transition API.
- The persisted canonical hypothesis remains the authoritative response.

## Persistence and Concurrency

- Extend the existing Hunt Hypothesis repository boundary with the smallest
  exact-state update required for activation.
- Acquire the existing repository-scoped inter-process lock before reading,
  validating and replacing repository content.
- While holding the lock, strictly validate the complete repository, locate
  exactly one hypothesis identity and re-check its expected status.
- Persist the complete canonical repository through the existing same-directory
  temporary-file, flush/fsync and atomic-replace behavior.
- Preserve all unaffected hypotheses byte-semantically/canonically and verify
  the resulting persisted hypothesis after replacement.
- Fail closed on duplicate identities, malformed repositories, lock failure,
  stale state, write/replace failure or ambiguous persisted state.
- A failed activation must leave the original repository unchanged and release
  the lock.

## API Boundary

- Add one narrow mutation endpoint for activating an exact hypothesis, for
  example `POST /api/hunt-hypotheses/{hypothesis_id}/activation`.
- The request may carry only the expected current status required for optimistic
  concurrency; it must not carry authoritative identity or target status.
- The server fixes the resulting status to `active` and returns the exact
  canonical persisted hypothesis.
- Preserve safe HTTP distinctions for not found, stale/invalid transition,
  unauthenticated, unauthorized, repository unavailable and repository
  integrity/persistence failure.
- Do not leak paths, credentials, session identifiers, CSRF values or raw
  internal exceptions.

## Audit

- Persist a secret-free audit record for every successful and rejected
  activation attempt through one explicit application-owned audit boundary.
- Record at minimum trusted timestamp, server-derived principal ID when safely
  available, operation, hypothesis ID, expected state, resulting/current state,
  authorization outcome and deterministic safe reason.
- Never persist credentials, cookies, Authorization headers, CSRF values,
  prompts, provider data or repository contents.
- Audit failure must fail closed before reporting activation success.

## Frontend

- Add an explicit activation action to `/threat-hunting/hypotheses` only for a
  canonical `draft` hypothesis and only when the authenticated session exposes
  the exact activation permission.
- Use the existing browser-session credentials, Origin and CSRF request pattern.
- Submit only the hypothesis identity from the route and expected status
  `draft`; never submit actor identity, permission or target status.
- Clearly state before and after activation that an active hypothesis is merely
  released for investigation and is not evidence, confirmed compromise or a
  validated conclusion.
- On success, refresh the canonical collection; after browser reload, the
  persisted `active` status must remain visible and no activation action may be
  offered for it.
- Preserve loading, empty, read error, creation, reference-resolution and
  URL-authoritative navigation behavior.
- Continue to show reference-resolution status truthfully. Missing,
  unavailable or unsupported references must not be invented, repaired or
  reinterpreted during activation.

## Required Tests

### Domain, Application and Repository

- exact `draft -> active` activation succeeds;
- every other source/target transition is rejected;
- resulting object remains canonical and immutable;
- expected-state mismatch/stale state fails without mutation;
- missing and duplicate hypothesis identities fail closed;
- existing hypotheses are preserved;
- malformed repository fails without modification;
- concurrent activation cannot lose data or activate twice;
- lock, temporary-write and atomic-replace failures preserve original data;
- lock is released on every terminal path;
- persisted active state survives a fresh repository read.

### Authentication, Authorization, API and Audit

- valid session, exact Origin, CSRF and permission permit activation;
- missing/invalid authentication returns `401`;
- authenticated principal without `hunt_hypothesis:activate` returns `403`;
- missing/wrong Origin or CSRF returns `403` before mutation;
- caller-supplied actor/permission/status authority is rejected;
- server-derived principal is used for authority and audit;
- not found, stale state, unavailable repository, integrity and persistence
  failures preserve their safe HTTP distinctions;
- successful and rejected attempts produce deterministic secret-free audit;
- audit failure cannot be reported as successful activation;
- responses, errors and audit contain no credential/session/CSRF material.

### Frontend

- activation is available only for `draft` and authorized session state;
- non-draft and unauthorized states cannot initiate activation;
- request uses `credentials: include`, CSRF and expected state only;
- no client-controlled actor, target status or permission is submitted;
- success refreshes the canonical list and displays `active` after reload;
- rejection/error does not fabricate state change;
- active semantics remain explicitly non-evidentiary;
- existing creation, reference resolution and routing behavior remains intact.

## Acceptance Criteria

- An authorized Local Operator can activate an existing draft through the UI.
- The exact same hypothesis is persisted as `active` and remains active after
  reload.
- Every unauthorized, stale, ambiguous or invalid attempt fails closed without
  repository mutation.
- Activation and rejection are audit-visible without sensitive data.
- No UI or API wording implies truth, evidence, execution success or compromise.
- No AI/provider execution, reference mutation, hunt execution or additional
  lifecycle transition is introduced.
- Full validation passes and the task is returned to Architect review without
  self-approval.

## Explicit Non-Goals

No AI-generated hypotheses, `hunt_hypothesis_proposal`, provider/model changes,

## Implementation Evidence

- Added an exact `HuntHypothesisActivationAuthority` requiring only
  `hunt_hypothesis:activate` from the server-derived Local Operator principal.
- Added a bounded application service that admits only expected `draft` state,
  persists only `active`, and records deterministic allowed/rejected audit
  events without secrets.
- Extended the existing file repository under its inter-process lock and
  atomic-write boundary with optimistic status verification and persisted
  result verification.
- Added `POST /api/hunt-hypotheses/{hypothesis_id}/activation`, protected only
  by the existing browser session plus exact Origin and session-bound CSRF.
- Added a draft-only UI action that submits no actor, permission or target
  status, refreshes the canonical collection, and preserves explicit
  non-evidentiary semantics.
- No AI/provider call, hunt execution, evidence generation, reference mutation
  or additional lifecycle transition was introduced.

### Bounded Rework after Architect Implementation Review

- Added a narrow HTTP activation-attempt auditor for session, Origin/CSRF and
  request-schema rejections that occur before the application service. It
  persists no headers, bodies, cookies, session identifiers, CSRF values or
  credentials and uses a nullable principal when authentication did not
  safely resolve.
- Added a write-ahead authorized-attempt event before mutation. The terminal
  success event is fsync-persisted through a callback while the repository
  lock is still held. If terminal audit persistence fails, the repository is
  atomically restored to its prior canonical document before the error is
  returned. The durable write-ahead event keeps an unrecoverable rollback
  failure inspectable rather than silent.
- Optimistic-concurrency conflicts now carry only the canonical current status
  and audit both expected and actual state while preserving HTTP 409.
- Added real concurrent activation and concurrent create/activate tests, plus
  lock, temporary-file, replace, post-replace verification, malformed data,
  duplicate identity, rollback and fresh-reader persistence coverage.
- The frontend now preserves the exact successful activation response before
  refreshing. A later collection-refresh failure retains the active state and
  produces a refresh-specific warning rather than falsely claiming activation
  failed.

### Bounded Rework #2 after Architect Implementation Review #2

- Audit JSONL updates now use same-directory copy-on-write persistence: the
  complete next audit document is written, flushed and fsync-confirmed before
  atomic replacement. A terminal event cannot become visible merely because
  bytes were written or flushed. `commit_state` and `mutation_state` separate
  authorized/pending, committed/persisted, verified rollback and reconciliation
  states.
- Write-ahead authorization records `current_status` as unknown until the
  repository has been canonically read under lock. Stale terminal evidence
  retains the requested `draft` state and the actual canonical current status.
- Terminal-audit failure restores the complete prior canonical document under
  the same repository lock, rereads it through the strict parser and compares
  the entire canonical tuple. Verified rollback and unverified recovery use
  distinct safe errors and audit outcomes; HTTP remains fail closed.
- Pre-service audit accepts only structurally canonical `hypothesis-*`
  identifiers of bounded length. Malformed, oversized, encoded or otherwise
  hostile route material is projected as `null`, never copied into audit.
- The complete pre-existing TO-ARCHITECT and TO-CODEX history is preserved
  beneath the minimal current TASK-0120 handoff section.
