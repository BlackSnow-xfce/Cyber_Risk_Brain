## Scope

Genau ein technologieunabhängiges Architekturartefakt `.ai/architecture/APPLICATION-SERVICES.md` erstellen.

Alle fachlich erforderlichen kanonischen Application Services definieren. Für jeden Application Service mindestens dokumentieren:

* eindeutiger Name
* fachlicher Zweck
* genau eine für die Orchestrierung verantwortliche Domain
* verwendete bestehende Domain Services
* koordinierte fachliche Use Cases
* verwendete bestehende Aggregate
* zulässige fachliche Abhängigkeiten
* nicht zulässige fachliche Abhängigkeiten
* fachliche Begründung seiner Existenz

Zusätzlich eindeutig festhalten:

* welche Orchestrierungsverantwortung der Application Service besitzt
* welche fachlichen Entscheidungen ausschließlich bei Domain Services verbleiben
* welche Zustands- und Konsistenzverantwortung ausschließlich bei Aggregates verbleibt
* welche Geschäftsregeln ausschließlich durch Aggregates, Domain Services und freigegebene Domain Policies bestimmt werden
* dass der Application Service keine Persistenz- oder Infrastrukturverantwortung besitzt

Nur Application Services aufnehmen, für die aus bestehenden Architekturartefakten ein konkreter fachlicher Use Case mit Orchestrierungsbedarf ableitbar ist. Keine Services zur künstlichen Vollständigkeit pro Domain, Workspace oder Rolle erfinden. Domains ohne erforderlichen Application Service ausdrücklich fachlich begründen.

## Architekturregeln

* Jeder Application Service besitzt genau einen eindeutigen Namen und genau eine für seinen Use Case verantwortliche Domain.
* Die verantwortliche Domain bezeichnet den fachlichen Ausgangspunkt der Orchestrierung und überträgt keine Domain- oder Aggregate-Ownership an den Application Layer.
* Application Services koordinieren ausschließlich vorhandene fachliche Fähigkeiten.
* Domain Services treffen die katalogisierten aggregateübergreifenden fachlichen Entscheidungen.
* Aggregates bleiben alleinige Zustands- und Konsistenzgrenzen.
* Application Services enthalten, duplizieren oder plausibilisieren keine Geschäftsregeln.
* Verwendete Domain Services und Aggregate müssen unverändert in den bestehenden Katalogen definiert sein.
* Zulässige Abhängigkeiten müssen `DOMAIN-DEPENDENCIES.md`, `AGGREGATE-RELATIONSHIPS.md` und ADR-0007 respektieren.
* Verbotene Domain-Rückreferenzen und Cross-Domain-Ownership bleiben verboten.
* Ein Application Service ist kein fachlicher Daten-Owner und keine neue Domain.
* Application Services besitzen weder Persistenz- noch Infrastrukturverantwortung.
* DecisionResult, Decision Evidence, Explainability und Execution Trace bleiben gemäß ADR-0001 bis ADR-0007 getrennt.
* Workspaces und Rollen begründen gemäß ADR-0005 keine Application-Service-Ownership.
* Bestehende Architekturartefakte und ADRs bleiben unverändert.
* Die Beschreibung bleibt technologie-, transport-, workspace-, rollen- und implementierungsunabhängig.
