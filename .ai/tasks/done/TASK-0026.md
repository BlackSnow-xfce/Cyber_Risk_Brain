Frontend Architecture and Implementation

## Ziel

Eine eigenständige Enterprise-Arbeitsoberfläche für Plattformadministratoren und Security Platform Engineers erstellen. Der Workspace dient ausschließlich Plattformbetrieb, Konfiguration, Governance und Überwachung. Er bildet keine operative Security-Analyse ab.

Der Task dient der Workspace-first Discovery und implementiert ausschließlich die Presentation Foundation dieser Rolle.

## Architekturgrundlagen

* ADR-0005 – Mission Console Workspace Architecture (`ACCEPTED`)
* Backend als fachliche Single Source of Truth
* bestehende App-Shell, Workspace Registry, Workspace-Navigation, Workspace Context und Workspace Switcher
* bestehendes Material-UI-Designsystem sowie React- und TypeScript-Regeln aus `AGENTS.md`

## Scope

### Workspace

Unter der bestehenden Workspace-Struktur einen eigenständigen Administrator-Workspace erstellen mit:

* eigenem Workspace-Root,
* eigenem Layout,
* eigenem Einstiegspunkt,
* eigener rollenspezifischer Navigation und Fokussteuerung,
* Integration des bereits registrierten `ADMINISTRATION` in bestehende Registry, Context und Outlet.

### Navigation

Die rollenspezifische Navigation enthält mindestens:

**Platform**

* System Overview
* Platform Health
* Services
* Integrations

**Administration**

* Users
* Roles
* Permissions
* Organizations

**Data**

* Connectors
* Data Sources
* Synchronization
* Import Status

**Intelligence**

* AI Models
* Policies
* Rules
* Prompt Library

**Operations**

* Audit Log
* Background Jobs
* Notifications

**Configuration**

* System Settings
* Feature Flags
* Licensing

Bezeichnungen dürfen an bestehende englische Benennungskonventionen angepasst werden. Keine zusätzlichen Bereiche zur künstlichen Vergrößerung der Navigation.

### Mission-Console-Startseite

Die Startseite bildet strukturell folgende Betriebsbereiche ab:

* Platform Health
* Connected Systems
* Connector Status
* Synchronization Overview
* AI Configuration
* User Management
* Audit Activity
* Background Jobs
* System Notifications

Nicht angebundene Bereiche werden transparent und eindeutig als Empty States gekennzeichnet. Die Oberfläche darf keine Health-Werte, Benutzerzahlen, Connectoren, AI-Modelle, Jobzustände oder andere Systemdaten vortäuschen.

### UI- und Integrationsregeln

* Bestehendes Designsystem, App-Shell und Workspace-Infrastruktur wiederverwenden.
* Bestehende Workspace Registry und Navigation erweitern, nicht duplizieren.
* `ADMINISTRATION` im bestehenden `WorkspaceOutlet` auf den eigenständigen Workspace abbilden.
* Sidebar-Fokussteuerung innerhalb der bestehenden Context-Grenze aktivieren.
* Workspace-Wechsel muss weiterhin funktionieren.
* Keine parallele Layout-, Navigation-, State- oder App-Shell-Architektur.
* Keine Businesslogik, Betriebsbewertung oder fachliche Statusableitung im Frontend.
* Keine Backend-Anbindung.
* Keine Fake-KPIs, simulierten Systemzustände, erfundenen Connectoren oder simulierten AI-Modelle.
* Keine funktionslosen Aktionen als produktiv darstellen.
* Wiederverwendbare Komponenten nur bei mindestens zwei realen Verwendungen extrahieren.
* Keine abstrakte Universal-Workspace-Komponente auf Vorrat erstellen.
* Vollständige Dateien und bestehende Import- und Verzeichniskonventionen verwenden.

## Rollenabgrenzung

Der Administrator Workspace dient Plattformbetrieb, Konfiguration, Governance und technischer Überwachung. Er ist kein SOC-, Threat-Hunting-, Incident-Response-, Risk-Manager- oder Executive-Workspace und enthält keine operative Security-Analyse.

Navigation, Fokuszustand und Seitenkomposition bleiben von allen anderen Rollen-Workspaces isoliert.

## Nicht Bestandteil

* Backend
* APIs
* Persistenz
* Connector Engine
* AI Engine
* User-Management-Backend
* Identity- oder Authorization-Implementierung
* Domainmodelle
* Businesslogik
* simulierte Produkt- oder Betriebsdaten
* fachliche Änderungen an anderen Rollen-Workspaces
