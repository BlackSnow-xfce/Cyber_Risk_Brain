## Scope

Genau ein technologieunabhängiges Architekturartefakt `.ai/architecture/COMMAND-QUERY-CATALOG.md` erstellen.

Alle fachlich erforderlichen kanonischen Commands und Queries aus den bestehenden Application Services ableiten. Keine Commands oder Queries zur künstlichen Vollständigkeit pro Domain, Aggregate, Workspace oder Rolle erfinden.

### Für jeden Command dokumentieren

* eindeutiger Name in fachlicher Befehlsform
* genau eine Owner Domain
* genau ein verantwortlicher bestehender Application Service
* betroffene bestehende Aggregate
* fachlicher Zweck
* fachliche Vorbedingungen
* erwartetes fachliches Ergebnis
* verwendete bestehende Domain Policies
* ausgelöste Domain Events ausschließlich als Referenzen auf bestehende Events

Falls ein fachlich erfolgreicher Command kein bestehendes Domain Event auslöst, ist dies ausdrücklich und fachlich zu begründen. Der Katalog darf kein neues Event definieren oder vorwegnehmen.

### Für jede Query dokumentieren

* eindeutiger Name in fachlicher Frage- oder Leseform
* genau eine Owner Domain
* genau ein verantwortlicher bestehender Application Service
* gelesene bestehende Aggregate
* fachlicher Zweck
* erwartetes fachliches Ergebnis
* fachliche Konsistenzanforderungen

Zusätzlich für Commands und Queries eindeutig festhalten:

* welche Orchestrierung beim Application Service verbleibt
* welche fachlichen Entscheidungen bei Domain Services verbleiben
* welche Zustands- und Konsistenzverantwortung bei Aggregates verbleibt
* dass weder Persistenz- noch Infrastrukturverantwortung übernommen wird

## Architekturregeln

* Commands und Queries sind strikt getrennt.
* Ein Command beabsichtigt genau eine klar abgegrenzte fachliche Zustandsänderung.
* Eine Query verändert niemals fachlichen Zustand und löst keine Domain Events aus.
* Jeder Command und jede Query besitzt genau eine Owner Domain und genau einen bestehenden verantwortlichen Application Service.
* Commands orchestrieren ausschließlich über bestehende Application Services.
* Queries werden ausschließlich durch bestehende Application Services fachlich verantwortet; technische Lesewege werden nicht definiert.
* Application Services koordinieren, Domain Services treffen fachliche Entscheidungen und Aggregates bleiben Konsistenzgrenzen.
* Commands und Queries enthalten keine eigene Geschäftslogik.
* Betroffene beziehungsweise gelesene Aggregate müssen aus `AGGREGATE-BOUNDARIES.md` stammen.
* Verwendete Policies müssen aus `DOMAIN-POLICIES.md` stammen.
* Referenzierte Events müssen unverändert aus `DOMAIN-EVENTS.md` stammen.
* Abhängigkeiten müssen `AGGREGATE-RELATIONSHIPS.md`, `DOMAIN-DEPENDENCIES.md` und ADR-0007 respektieren.
* Commands dürfen keine Aggregate fremder Domains direkt verändern und keine Cross-Domain-Ownership erzeugen.
* Queries dürfen fehlende Fakten weder erzeugen noch plausibilisieren.
* DecisionResult, Decision Evidence, Explainability und Execution Trace bleiben gemäß ADR-0001 bis ADR-0007 getrennt.
* Workspaces und Rollen begründen keine Command-, Query- oder Daten-Ownership.
* Der Katalog bleibt technologie-, transport-, workspace-, rollen- und implementierungsunabhängig.
* Bestehende Architekturartefakte und ADRs bleiben unverändert.
