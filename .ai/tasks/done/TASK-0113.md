# TASK-0113 - Hunt Hypothesis Read Path Foundation

**Status:** DONE / PASS / APPROVED
**Reviewer:** Architect
**Product Owner Live Acceptance:** PASS
**Track:** POST-MVP Threat Hunter

## Objective

Establish the first truthful, read-only product path for the canonical
`HuntHypothesis 1.0` domain contract:

`configured JSON repository -> query service -> API -> Threat Hunter UI`

## Acceptance Criteria

- An explicitly configured JSON-file repository loads only canonical
  `HuntHypothesis 1.0` records.
- Missing configuration is transparent and maps to HTTP 503.
- A configured empty repository returns HTTP 200 and an empty collection.
- Malformed records, duplicate IDs, invalid statuses, timestamps and typed
  references fail closed; invalid records are never skipped.
- `GET /api/hunt-hypotheses` exposes canonical read-only projections.
- `/threat-hunting/hypotheses` distinguishes loading, empty, error and
  populated states.
- Populated cards expose only canonical fields and describe typed references
  as unresolved pointers, not confirmed Findings or compromise.
- Existing Threat Hunter navigation and URL-authoritative behavior remain.
- No runtime hypothesis data, write path, AI generation or hunt execution is
  introduced.

## Implementation Evidence

The read path uses `HUNT_HYPOTHESIS_REPOSITORY_PATH` with no default. The
strict reader validates the complete JSON document and constructs the
authoritative domain objects before returning any collection. The application
query service is read-only. The API returns 503 for unavailable configuration,
500 for invalid configured data, and 200 for canonical collections including
an empty collection.

The Hypotheses route loads the API and renders explicit loading, repository
error, truthful empty, and populated states. Persisted typed references remain
labelled as unresolved pointers. No hypothesis is presented as a Finding or
confirmed compromise.
