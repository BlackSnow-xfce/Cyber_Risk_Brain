## Implementierung

Implementiert wurde eine reine serverseitige Boundary in
`core/incident_response/lifecycle.py`:

* `IncidentLifecycleTransitionRequest` verlangt Incident-ID, erwarteten
  Status, Zielstatus, `IncidentPrincipalReference`, UTC-/timezone-aware
  Timestamp und nicht-leere Justification.
* `IncidentLifecycleTransitionService` validiert deterministisch die sechs in
  ADR-0009 erlaubten Transitionen:
  `OPEN -> INVESTIGATING`, `OPEN -> CLOSED`,
  `INVESTIGATING -> RESOLVED`, `RESOLVED -> INVESTIGATING`,
  `RESOLVED -> CLOSED`, `CLOSED -> INVESTIGATING`.
* Self-Transitions, Status-/Incident-ID-Mismatches und zeitlich ruecklaeufige
  Transitions werden fail-closed als `INVALID` zurueckgegeben.
* `IncidentLifecycleTransitionResult` unterscheidet `ALLOWED` und `INVALID`.
  Bei Erfolg wird ein unveraenderlicher, aktualisierter Context projiziert; der
  Eingabe-Context bleibt unveraendert.

Es existiert im bestehenden `SecurityIncidentContext` keine Incident-Version.
Daher wurde keine Concurrency-/Versionssemantik erfunden. Ebenso wird keine
`IncidentActivity` automatisch erzeugt: Ohne Persistenz-, Sequenz- oder
Historien-Boundary waere dies eine neue Source of Truth. Eine erfolgreiche
Transition hat ausschliesslich den bestehenden Incident-Context als Ergebnis.

Decision Lifecycle (ADR-0008), Findings, Assets, TI, Evidence, Risk, Decision,
Execution Trace, API, UI, AuthZ und Response-Ausfuehrung bleiben unberuehrt.
