# TASK-0115 - Authenticated Local Operator and Hunt Hypothesis Write-Authority Foundation

**Status:** DONE / PASS / APPROVED
**Reviewer:** Architect
**Product Owner Live Acceptance:** PASS
**Local Operator Live Authentication:** PASS
**Track:** POST-MVP Threat Hunter

## Objective

Establish a secured Single-User Local Operator Mode that derives a human
principal from trusted server configuration and request-bound credential
verification. Provide a separate, reusable authorization boundary for
`hunt_hypothesis:create` without implementing any write path.

## Acceptance Criteria

- Local Operator mode has no enabled or anonymous default.
- Principal identity and permissions come only from validated server-side
  configuration, never caller-supplied identity or permission fields.
- Bearer credentials are compared safely, never returned, logged or persisted,
  and malformed, missing or invalid credentials return 401.
- Unavailable configuration returns 503; structurally untrustworthy
  configuration returns a non-sensitive 500 response.
- Authenticated principals without `hunt_hypothesis:create` are rejected by
  the reusable write-authority boundary with 403.
- `GET /api/operator/me` returns only safe principal metadata.
- Authenticated local browser origins are explicit, local and configured;
  wildcard origins and credentialed CORS are not permitted.
- The authority decision supplies an audit-ready principal ID, operation,
  trusted server timestamp and authorization outcome.
- No Hunt Hypothesis repository write, creation endpoint/UI, lifecycle
  transition or AI-generated content is introduced.

## Implementation Evidence

`LocalOperatorAuthenticator` validates the enabled mode, configured identity,
strong local token, exact permission allowlist and explicit local origins. It
uses a strict Bearer header and constant-time token comparison. The immutable
`AuthenticatedPrincipal` contains only server-derived metadata.

`HuntHypothesisWriteAuthority` separately evaluates the exact
`hunt_hypothesis:create` permission and emits an immutable audit-ready decision.
The verification endpoint returns the configured principal projection only.
Because the credential is supplied in an explicit Authorization header rather
than an ambient browser cookie, classical cookie-based CSRF does not apply in
the same way; explicit local CORS remains a defense-in-depth boundary.
