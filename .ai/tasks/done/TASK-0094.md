Status: DONE

## Verified live path

Before this task, `FindingExplanationUseCase` loaded a finding directly from
`FindingsQueryService`, then built risk/context input and invoked the existing
model-egress and output-security path. `FindingTrustedRetrievalService`,
`BoundAIContext` and `AIContextAdmissionPolicy` existed but were isolated.

## MVP authorization boundary

The current API has no authenticated principal or enterprise IAM context. The
MVP boundary therefore requires an explicit, server-controlled
`AI_FINDING_EXPLANATION_ALLOWED_IDS` environment setting. Each requested ID is
bound to a single `AIResourceReference`, operation `retrieve_finding`, subject
`mvp:configured-finding-explanation`, and `INTERNAL` classification. Missing
configuration denies all requests; this is not an IAM implementation and does
not provide wildcard or allow-all semantics.

## Implementation

`FindingExplanationUseCase` now obtains the explicit authorization scope before
calling `FindingTrustedRetrievalService`. The trusted service performs the
scope, operation, classification and exact identity checks before its single
repository read and returns the authoritative finding together with its
immutable `BoundAIContext`. `AIContextAdmissionPolicy` must then return ADMIT
before asset/risk context construction, model egress, provider invocation and
the existing output disclosure policy/guard.

Authorization or admission failure is fail-closed. The existing model egress
allowlist and output security controls remain unchanged.
