## Repository-Boundary und Persistenz

`IncidentContextRepository` ist die minimale Query-/Save-Boundary. Der
`FileIncidentContextRepository` persistiert ausschliesslich den kanonischen
Context in einer strikt validierten JSON-Datei unter der Environment Reference
`INCIDENT_CONTEXT_PATH`.

Format:

`{"contractVersion":"1.0","incidents":[...]}`

Die JSON-Struktur ist nur Transport-/Persistenzformat; es wurde kein neues
fachliches Incident-Modell eingefuehrt. Lifecycle, Owner, Participants,
Relationships und Contract-Version werden beim Laden erneut durch den
kanonischen `SecurityIncidentContext` validiert. Unbekannte IDs liefern
`None`; fehlende Konfiguration oder unlesbare Dateien liefern einen
kontrollierten Configuration-Fehler; ungueltige Daten werden nicht repariert.

`IncidentContextCreationService` ist eine interne serverseitige Creation-
Boundary. Sie akzeptiert ausschliesslich einen vollstaendig validierten
`SecurityIncidentContext` und delegiert an das Repository. Es gibt keine
oeffentliche Write-API, keine automatische Incident-Erzeugung und keine
Duplikation von Findings, Assets, TI oder Evidence.

## Query-/API-Wiring

`get_security_incident_context_reader()` verwendet nun den konfigurierten
File-Repository-Reader. Der bestehende Endpoint
`GET /api/incidents/{incident_id}/command-center` bleibt fachlich und im
Response-Vertrag unveraendert. Persistierte Incidents werden ueber den
bestehenden Query-Service projiziert; unbekannte IDs bleiben HTTP 404,
fehlende Konfiguration wird HTTP 503.
