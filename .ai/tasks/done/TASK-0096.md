## Architect-requested provider root-cause analysis

The live application path was traced without changing code or configuration:

`FindingExplanationUseCase` → trusted retrieval/bound context/admission →
`FindingExplanationInputBuilder` → `FindingExplanationService` →
`OpenAIFindingExplanationModel`.

The provider call is reached. The adapter uses the `requests` library directly
(no OpenAI SDK package is installed), the OpenAI Responses API endpoint
`https://api.openai.com/v1/responses`, model `gpt-5.6-terra`, JSON-schema strict
structured output and the configured 30-second timeout. The adapter constructs
the request from `explanation_input.model_egress_data()`, whose positive
allowlist remains limited to `finding.title` and `finding.vendor_severity`.

A single controlled diagnostic invocation captured the non-sensitive exception
class `requests.exceptions.ProxyError` while attempting the HTTPS POST. No
HTTP status or provider response body was received; the exception is converted
by the adapter to `FindingExplanationProviderError`, and the application maps
that to `generation_status=PROVIDER_ERROR` with no model output. The configured
model is therefore not the demonstrated failure cause, and no response-schema
parsing was reached.

Root-cause classification: **F. NETWORK / PROVIDER AVAILABILITY**. Evidence is
the `ProxyError` before an HTTP response, with the existing runtime exposing
proxy environment configuration. The API's HTTP 200 is only the application's
controlled result envelope, not a successful provider response.

Recommended remediation (not implemented): **CONFIG-ONLY**, **SMALL** — repair
or provide the approved outbound HTTPS proxy/network configuration for the
backend runtime, then repeat the same live acceptance. No model change, SDK
upgrade, payload change, retry, or application-code change is indicated by
this diagnosis.

The input security chain is intact through the attempted provider boundary;
output disclosure policy and guard are not reached because no provider output
exists. TASK-0096 remains REVIEW/BLOCKED and TASK-0097 was not created.

## INVALID_OUTPUT response root-cause analysis

One additional controlled adapter-path call captured only non-sensitive
response metadata. The provider returned HTTP `200` with
`Content-Type: application/json`. The top-level response was a JSON object
containing normal Responses fields including `output`, `status`, `model`,
`text` and `usage`. `output` was a list with one item of type `message`; that
item contained one content item of type `output_text`. No raw response content
was stored in AIDP.

The request sent by PredatorAI was confirmed as model `gpt-5.6-terra`, input
roles `developer` and `user`, `text.format.type=json_schema`, schema name
`finding_explanation`, `strict=true`, and required top-level fields
`summary`, `technical_reasoning`, `organizational_relevance` and
`uncertainty_statement`.

This response shape reaches
`OpenAIFindingExplanationModel._extract_output_text`. The resulting
`INVALID_OUTPUT` is raised before `FindingExplanationService._validate_output`
and therefore before application result-schema validation. The envelope is
valid JSON, but the extracted output content is not accepted as parseable
FindingExplanation JSON by the adapter (the exact content is intentionally not
retained or copied). The envelope and item shape conform; the model-output
content does not satisfy the adapter's JSON boundary.

Primary classification: **B. PROVIDER NON-CONFORMING OUTPUT**. Evidence is the
HTTP-success response with the expected `message`/`output_text` structure plus
the deterministic `INVALID_OUTPUT` result before application schema
validation. This is not an HTTP transport failure and not an application
`FindingExplanationResult` schema mismatch.

Recommended remediation (not implemented): **PROVIDER/MODEL CHANGE REQUIRED**,
**SMALL** — make the selected model/structured-output configuration return
parseable `finding_explanation` JSON, then repeat acceptance. No fallback
parsing, prompt/schema change, model switch or adapter change was performed.

## Provider/model compatibility check

The official OpenAI documentation describes the Responses API and
`text.format.type=json_schema` Structured Outputs contract, including strict
schema adherence for models that support it ([Responses API reference](https://platform.openai.com/docs/api-reference/responses-streaming/response/refusal/delta?lang=python)).
The official published model/endpoint table lists concrete Responses-capable
model IDs such as `gpt-5-2025-08-07`, `gpt-5-mini-2025-08-07`, `gpt-4.1` and
others, but does not list `gpt-5.6-terra` ([OpenAI model/endpoint table](https://platform.openai.com/docs/models/default-usage-policies-by-endpoint)).
Compatibility of `gpt-5.6-terra` with this Structured Outputs contract is
therefore **NOT VERIFIED** from official documentation.

Repository inspection shows `gpt-5.6-terra` is not read from settings or an
environment variable. It is hardcoded as `OpenAIFindingExplanationModel.model_id`
in `infrastructure/openai_finding_explanation.py`; only the API key and timeout
come from settings. Consequently, a CONFIG-ONLY model switch is unavailable.
Per the task stop condition, no provider call, model rotation or product-code
change was performed.

Remediation classification: **BLOCKED-BY-HARDCODED-CONFIG**. The smallest
future remediation is **CODE CHANGE REQUIRED**, **SMALL**, limited to making
the existing model identifier configurable or replacing that single adapter
constant with an officially supported Responses/Structured-Outputs model after
Architect approval. TASK-0096 remains REVIEW/BLOCKED and TASK-0097 was not
created.

## Final schema-versus-validator contract comparison

The last permitted structural diagnostic call returned HTTP 200,
`status=completed`, and syntactically valid JSON. The actual runtime shapes
were:

| Field | Provider JSON schema | `_validate_output` expectation | Actual runtime shape |
|---|---|---|---|
| `summary` | object `{kind,text,basis_fact_ids}` | one `FindingExplanationStatement` with semantic enum/reference rules | object with those three keys |
| `technical_reasoning` | array of statement objects | non-empty tuple of statements, each passing semantic rules | array of 2 statement objects |
| `organizational_relevance` | array of statement objects | tuple of statements, every item must be `CONTEXTUAL_INFERENCE` | array of 1 statement object |
| `uncertainty_statement` | object `{kind,text,basis_fact_ids}` | one `FindingExplanationStatement` with semantic enum/reference rules | object with those three keys |

The schema and runtime agree on top-level presence, object/array structure and
statement key/type structure. The application validator additionally enforces
rules not represented in the provider schema: non-empty technical reasoning;
valid `InferenceKind`; known fact IDs; contextual statements requiring at least
one fact; general reasoning forbidding fact IDs; and organizational relevance
being contextual inference only. The JSON schema permits the broader enum and
string-array shapes, so it cannot guarantee those application semantics.

The first failing semantic field/value cannot be identified from the retained
non-content evidence without exposing model values or making another provider
call. The deterministic root cause is nevertheless established: the declared
provider schema is weaker than the authoritative application contract, and
`_validate_output` rejects a syntactically valid response on one of those
semantic rules. Primary classification: **B. APPLICATION VALIDATOR DOES NOT
MATCH DECLARED PROVIDER SCHEMA**. The authoritative contract is the
`FindingExplanationModelOutput` / `FindingExplanationStatement` contract
implemented by `_validate_output`, not the weaker JSON schema alone.

Correct remediation direction (not implemented): **CODE CHANGE**, **SMALL** —
align the existing provider schema with the authoritative semantic contract
(without weakening validation), or introduce an explicit typed mapping that
enforces the same rules before result construction. No security control,
Finding field allowlist or output acceptance rule was changed.
