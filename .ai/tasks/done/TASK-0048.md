## Verbindliche Product-Owner-Klassifikation

Für den kontrollierten lokalen DVWA-Lab-Kontext gilt ausschließlich folgende explizite autoritative Zuordnung:

| Aussage | Freigegebener Wert |
|---|---|
| Observed Identifier Type | `ip_address` |
| Observed Identifier | `172.18.0.18` |
| Canonical PredatorAI Asset ID | `asset-lab-dvwa-001` |
| Asset Criticality | `LOW` |
| Source Reference | `product-owner:dvwa-lab-classification` |

Semantik der Klassifikation:

* `LOW` ist eine ausdrückliche Product-Owner-Aussage über die Unternehmensrelevanz dieses kontrollierten Lab-Assets.
* Das Asset besitzt im aktuellen PredatorAI-Lab-Kontext keine produktive Business-Funktion und wurde deshalb mit `Asset Criticality LOW` klassifiziert.
* Die Klassifikation wurde nicht aus Greenbone Vendor Severity, DVWA, Docker, IP-Adresse, Port, Erreichbarkeit, Scanner-Ergebnis oder technischer Verwundbarkeit abgeleitet.
* Technische Finding Severity und Asset Criticality beantworten unterschiedliche Fragen und bleiben strikt getrennt.
* Eine Kombination aus `vendor_severity=Critical`, `Asset Criticality=LOW` und `Risk Readiness=INSUFFICIENT_CONTEXT` ist fachlich korrekt und ausdrücklich zu unterstützen.

## Typ

Backend Architecture/Contract Implementation – Controlled Enterprise Asset Context

## Ziel

Einen realen scanner-beobachteten Host-Identifier explizit und nachvollziehbar auf einen vorhandenen, autoritativ klassifizierten Enterprise-Asset-Kontext auflösen und ausschließlich dessen `Asset Criticality` in die bestehende Risk-Readiness-Grenze projizieren.

Erwarteter Pfad:

```text
UniversalFinding.asset (scanner-observed host identifier)
-> explicit identifier resolution
-> configured authoritative Asset Context source
-> canonical Asset identity + Asset Criticality + source reference
-> RiskAssessmentInput.business_criticality = AUTHORITATIVE(value, source)
-> übrige Risk-Faktoren bleiben NOT_EVALUATED
-> INSUFFICIENT_CONTEXT, score=None
```

Ein nicht auflösbarer Identifier bleibt `UNKNOWN`. Es gibt keinen `LOW`-Default.

## Architecture-Discovery-Befund

### Vorhandene fachliche Architektur

Die Architecture Baseline definiert bereits:

* Enterprise Context als alleinigen Owner von Asset Identity und Asset Criticality,
* das Asset Context Aggregate mit Root `Asset`,
* `Asset Criticality` getrennt von `Business Service Criticality`,
* den Enterprise Context Classification Service und die Authoritative Context Classification Policy,
* Command und Query für Klassifikation beziehungsweise Lesen vorhandener Context-Aussagen,
* `Asset Context Classified` als fachliches Ereignis,
* eine zulässige Herkunftsreferenz zum Integration Aggregate beziehungsweise dessen Source Lineage.

Diese Fähigkeiten sind im aktuellen Backend noch nicht als Asset-Modell, Registry, Repository oder Resolution Service implementiert.

### Nicht autoritative Bestände

* `UniversalFinding.asset` enthält beim Greenbone-Pfad den Scanner-Hosttext. Für den realen Export ist dies die IP-Adresse `172.18.0.18`; sie ist keine kanonische Enterprise-Asset-ID.
* Frontend-`Asset`, `AssetContext` und `MockAssetRepository` sind Presentation-/Demo-Daten und keine Backend Source of Truth.
* Legacy-Connector-`criticality` und `core.decision.business_context.BusinessContextEngine` verwenden statische beziehungsweise Defaultwerte und sind keine autoritative Quelle für das reale Asset.
* Es existiert keine implementierte CMDB-, Inventory-, Registry-, Alias- oder Asset-Resolution-Fähigkeit im Backend.

## Autoritative Eingabe

Der Product Owner hat den einzelnen kontrollierten Asset-Context-Datensatz vollständig autorisiert. Der Implementation Agent muss exakt die dokumentierten Werte verwenden und darf sie weder umdeuten noch aus technischen Merkmalen neu ableiten.

Optional dürfen ausschließlich tatsächlich vorhandene zusätzliche Source-Metadaten übernommen werden. TASK-0048 darf Source-Owner, Source-Version oder Klassifikationszeitpunkt nicht erfinden und führt keine allgemeine Provenance-Versionierungsarchitektur ein.

## Scope

### 1. Minimaler Asset-Context-Vertrag

* Einen kleinen, immutable behandelten Backend-Vertrag für kanonische Asset-ID, `Asset Criticality`, explizite beobachtete Identifier und Source Reference implementieren.
* Asset Criticality ausschließlich mit den bereits in TASK-0047 definierten Werten abbilden; kein paralleles Criticality-Modell erzeugen.
* IP-Adresse, Hostname und kanonische Asset-ID semantisch getrennt halten.
* Keine Crown-Jewel-, Exposure-, Ownership- oder Business-Service-Aussage ergänzen.

### 2. Kontrollierte konfigurierte Quelle

* Die vorhandene Settings-/Environment-Konvention für den Pfad zu einem explizit bereitgestellten, kontrollierten Asset-Context-Dokument verwenden.
* Kein Benutzer-/Desktop-Pfad und keinen konkreten Asset-Wert im Produktcode hardcodieren.
* Keine automatische Dateisuche und keinen Request-Dateipfad einführen.
* Für automatisierte Tests ausschließlich ein minimales synthetisches Testdokument verwenden.
* Das Product-Owner-autorisierte reale Lab-Dokument nicht automatisch committen.
* Keine Datenbank, CMDB-Integration oder neue Persistenzarchitektur einführen.

### 3. Explizite Asset Resolution

* Einen beobachteten Identifier nur über eine ausdrücklich konfigurierte Identifier-Zuordnung auf eine kanonische Asset-ID auflösen.
* Für den realen Host darf die IP-Syntax erkannt werden; daraus darf aber keine Enterprise Identity abgeleitet werden.
* Kein Match: kein Asset Context, Criticality bleibt `UNKNOWN`.
* Mehrdeutige oder widersprüchliche Zuordnung: kontrollierter Fehler; keine heuristische Auswahl.
* Keine generische CMDB-, Alias- oder Multi-Source-Abstraktion über den beobachteten Scope hinaus entwickeln.

### 4. Risk-Readiness-Integration

* Die bestehende `UniversalFinding`-Projektion um einen explizit bereitgestellten, aufgelösten Asset Context koordinieren, ohne `UniversalFinding` zu erweitern.
* Bei erfolgreicher Resolution ausschließlich `RiskAssessmentInput.business_criticality` als `AUTHORITATIVE(<AssetCriticality>, <source reference>)` setzen.
* Bei unbekanntem Asset `business_criticality=UNKNOWN` erhalten.
* Exposure, Detection, Threat Intelligence und MITRE unverändert `NOT_EVALUATED` lassen.
* Wegen der verbleibenden fehlenden Inputs weiterhin `INSUFFICIENT_CONTEXT` und `score=None` erwarten.
* Keine RiskEngine-Delegation für den realen Lab-Datensatz erwarten oder erzwingen.

### 5. Reale Validierung

* realen Greenbone-Export über `GREENBONE_REPORT_PATH` laden,
* `172.18.0.18` als beobachteten `ip_address`-Identifier behandeln,
* explizite Zuordnung zu `asset-lab-dvwa-001` bestätigen,
* `Asset Criticality LOW` mit Source Reference `product-owner:dvwa-lab-classification` als autoritativ bestätigen,
* übrige Risk-Faktoren als `NOT_EVALUATED` bestätigen,
* `INSUFFICIENT_CONTEXT`, `score=None` und keine RiskEngine-Ausführung bestätigen.

## Akzeptanzkriterien

* Scanner-Identifier und kanonische Asset-ID sind getrennt modelliert.
* Nur eine explizite Identifier-Zuordnung kann einen Asset Context liefern.
* Bekannter Identifier liefert die Product-Owner-autorisierte Asset-ID, Asset Criticality und Source Reference.
* Unbekannter Identifier liefert keinen Kontext und bleibt `UNKNOWN`; kein `LOW`-Default.
* Mehrdeutige oder ungültige Daten schlagen kontrolliert fehl.
* Die Asset Criticality wird als bestehender `AssetCriticality`-Wert in `RiskAssessmentInput.business_criticality` projiziert.
* Vendor Severity, IP-Adresse, DVWA-Eigenschaft und Scanner-Erreichbarkeit beeinflussen die Criticality nicht.
* Exposure, Detection, TI und MITRE bleiben `NOT_EVALUATED`.
* Das reale Assessment bleibt `INSUFFICIENT_CONTEXT` mit `score=None` und ohne Engine-Aufruf.
* Source Reference bleibt im vorhandenen `RiskInputValue.source` nachvollziehbar.
* Keine Datenbank, keine neue Asset-Gesamtarchitektur und keine ausgeschlossene Integration entsteht.
